# 手机对话排队与重试修复（2026-10-11）

本次修改只处理手机对话发送链路及既有排队条的必要状态，不重做界面、样式或动画。没有发布、部署或调用真实模型，也没有读取用户凭据。

## 已定位的问题

1. 连续提交的排队消息会拼成一段文字，多个独立任务失去边界。
2. 合并图片后 `slice(0, 4)` 会静默丢掉后面的图片。
3. `deliver()` 捕获错误后正常返回，排队 effect 却把它当成功并清掉原消息。
4. 如果仅保留队列但不区分错误状态，确定性拒绝可能触发不停自动重试。
5. 接受第一条后，手机还未观察到运行状态时，第二条可能提前发出。
6. 普通草稿不保存图片。取回排队消息后立即移除持久队列，重启可能丢掉图片。
7. 按相册缓存 URI 的短哈希复用快照，会把复用同一路径的新照片与旧照片混淆。
8. 失败轮次的“重试”只取上一条用户文字，图片没有一同重发。
9. 排队记录超过二十个会话时，旧记录会被静默淘汰。
10. 主对话里的子智能体链接会直接使用未经桌面授权目录核实的 handle 路由，可能把原生子会话错误降级成 CLI。
11. 恢复时一次读取全部排队图片的 base64，会把几十张图片同时留在 JS 内存；排队图片也没有可信的解绑回收范围或累计容量上限。
12. 草稿只按中转站 ID 隔离，相同站点重新配对可能显示旧凭据代次的私有文字。

## 修复行为

- 每次提交是独立 FIFO 记录，每会话最多十条、每条最多四张图，超限明确拒绝而不是截断。最多二十个排队会话；第二十一个不驱逐旧记录。
- 接受排队前先完成持久写入。写入失败时，原文字与图片仍留在输入框；保存期间禁止再次提交及编辑，避免迟到清空新草稿。
- 记录绑定原站点/设备/会话草稿 key、配对 scope、API 身份及冻结的模型、强度、账号 handle、执行 surface。来源改变后暂停，不能暗中换一把 Key 自动执行旧任务。
- `waiting / attempting / blocked` 区分等待、发送中与暂停。发命令前持久化 `attempting`；重启恢复该状态时转为暂停，不能创建新的请求重复执行。
- `deliver()` 明确返回送达、交给持久回执、确定拒绝或界面已失效。只有前两种会移除队首。确定拒绝保留暂停记录，不自动循环。
- 断网/结果未知时，只有精确匹配 `requestId` 且确认由本次提交建立的实际持久回执才能接管新队首，不能以同文判断归属。新排队提交在回执原子选择处禁止复用旧回执，避免同文但图片/API/模型不同的新提交被误清除。明确重试才复用原请求 ID；后续队列不能绕过待确认消息。
- 回执写入使用候选列表：SQLite 提交成功后才发布内存状态。新回执提交失败不执行任务；电脑已确认执行后，本地清理失败保留原回执 ID，不把它当作任务未执行。
- 回执首次读取异常、损坏 JSON、超量、非法行、重复会话 owner 或同 scope/requestId 不能被过滤成空列表；不覆盖原记录、不发新操作。旧无摘要图片记录保留，但无法安全恢复的原图重试仍拒绝；迟到磁盘读不能覆盖新提交。
- 队列推进必须观察到上一条发送之后的新终止轮次，不能把发送前的空闲状态误认为上一条已经完成。
- “取消排队，放回输入框”暂停自动执行并进入编辑；持久记录保留到用户明确再次发送/重新排队成功，后面的任务不能抢先执行。
- 丢失的图片保持恢复要求，用户需要用现有图片选择入口完整重选，再明确发送；不会仅发文字。正常完整图片可由用户在编辑时明确增删。
- 新快照使用实际 base64 的 SHA-256 标识，按配对 scope 的 SHA-256 写入私有 `remote-images-v2/<scope-hash>/queue-<content-hash>.<ext>`。缓存路径被复用时，排队快照仍与当次提交的字节一致；新内容不会覆盖旧内容寻址路径。
- 文件字节写入前先持久记录精确 produced-file intent。写入或队列提交失败也不靠扫描目录寻找“孤儿”。路径只接受本实现精确生成的文件，目录、任意外部路径和旧 `remote-queued/` 文件都不是删除候选。
- 队列保存返回无 base64 的持久图片元数据；页面采用返回记录而不是保留原图片字节。恢复仅查元数据和存在性；重存既有新快照也不读全队列字节。仅发送队首时读取最多四张图，并校验该 managed 文件的实际字节与内容摘要一致，读取完成后再检查配对/API 身份。
- 单张仍最多 8 MiB。新 managed 存储的 queue/submission 每一种、每个 scope 各最多 128 MiB，全局最多 512 MiB/2048 个文件；达到限制明确拒绝，不能无限积累。该上限不包含旧兼容目录或别的应用缓存。
- `clearRemoteCache(scope)` 接入精确排队清理：先持久化 scope 退役围栏，再仅删除该 scope 清单内明确拥有且不是目录的文件；迟到队列/普通文字写入不能复活已退役 scope。删除失败保留清单记录，可用同一 exact scope 重试。
- 普通文字及排队草稿 key 改为 `operationScope|deviceId|thread`；不自动迁移旧未标凭据草稿。模型偏好 key 保持原样。清理只匹配确切 scope 行与私有 key；旧裸 connection ID 的兼容清理不覆盖其 `credential:` 子命名空间，新配对不会被旧清理误删。
- 失败轮次重试使用完整上一条用户消息；有图片时，按同一会话附件引用恢复/读取全部本地字节后才重发。外部 URL 不下载。旧记录缺少可恢复元数据时明确拒绝文字降级。
- 手机切换页面、隐藏、卸载或配对 scope 更换后，迟到持久写入不能触发发送；API 身份在写入等待期间改变也会在命令发送前暂停。
- 原生主对话点击子智能体只打开并定位侧边栏。实际打开交给侧边栏当前精确会话授权目录；原始 handle 本身不代表访问许可。
- 上游正在内部重试的 notice 不展示更换 Key/模型操作；只有终止失败才作为对应错误引导。

## 边界与待验收

- 这是手机本地持久队列，不是电脑端常驻调度器。手机退出或被系统挂起时不会主动提交新的排队任务；重新打开原会话后才推进。已经送达电脑的任务不因此停止。
- 正在发送后进程崩溃、或成功后队列清理写入失败，会优先暂停并要求核对，不能从“可能已发”推断“从未发”。不会自动制造新请求 ID。
- 普通尚未提交/排队的输入框仍只有文字草稿持久化；本次没有把所有普通图片草稿改造成另一个完整附件编辑器。已发送/待发送的受管图片会走 queue handoff，不代表任意 picker URI 都会被托管。
- 新 managed 文件现在有有限容量和 exact-scope 解绑清理；仍**不按消息完成或年龄自动回收**。`store.durableAttachmentUri()` 目前可能把 queue URI 直接用于持久回执/timeline/cache，引用关系尚未完整转交，提前 GC 会误删历史图片。因此快照保留到该 exact 配对退役，不扫描目录，不猜测孤儿。
- `handoffQueuedImages(scope, images)` 已接入 `store.ts` 的新任务与既有会话发送链：在附件引用、持久回执和首个网络命令冻结前完成 queue URI → 内容寻址 submission 的所有权转移；scope/字节摘要不一致会拒绝发送，不会把 queue URI 写入回执或历史。普通文字/普通 picker 发送仍不加载 queue 模块。
- 附件读取缓存按 `credential → device/session` 嵌套目录隔离；解除配对会精确删除该 credential 的目录并中止进行中的子目录读取，旧连接不能在撤销后重新写回图片缓存。跨 credential 隔离和 in-flight abort 有独立回归测试。
- 旧 flat `remote-queued/` 无可信 produced manifest，普通 legacy 草稿无完整凭据标识，均不猜删、不自动迁移；它们不受本次 v2 存储预算覆盖。需要单独、有明确授权的迁移/清理方案。
- 磁盘/SQLite/权限错误时，清理按现有解绑流程 best effort，不能承诺字节已全部抹除。已成功写入的退役围栏阻止晚写；删除失败记录保留，可重复 exact-scope 清理。损坏清单 fail closed，不因追求“清完”改成全目录删除。
- 该阶段最初发现的 PendingDelivery retired-scope P1 已由协调集成任务修复：明确撤销时精确退役消息与问答回执、围栏晚写、处理部分解绑和新 QR 竞态。匿名发现失败不当作配对失效，普通缓存清理不删除仍有效的不确定操作。新文件/链接接入前稳定基线为 82 suites、1157 tests 通过（8 项跳过），详见 [协调验收记录](CODEX-CONVERSATION-AUDIT-20261011.md)。此计数不作为后续文件/链接功能验收证据。
- 需要 Android 真机验证图片权限、系统挂起/恢复、SQLite 写入失败、长时间离线和 native Codex 真实授权目录。合成测试不能代替这些验收。
